# SmartphoneMonitor Implementation Plan

## Цель

Сформировать конкретный план доработок для `SmartphoneMonitor`, основанный на внутреннем аудите `WebScraperService` и `DataAnalysisService`.

## Состояние сейчас

* Парсер получает данные из `999.md/graphql` и затем делает дополнительные HTML-запросы для контактов, описания и просмотров.
* Анализ строится на сложной формуле `score`, которая комбинирует отклонение цены, свежесть, просмотры, срочность, дефекты, ремонт и сравнение с розничными акциями.
* В базе хранится история цен, blacklist номера и логины, а также настройки приложения.

## Основные проблемы

1. Хрупкость парсера:
   - жесткая зависимость от конкретных `featureId`/`subCategoryId` GraphQL;
   - нестабильный HTML-парсинг для деталей объявления;
   - неправильная логика определения блокировки ответа;
   - отсутствие версионирования парсера/API.

2. Непрозрачный скоринг:
   - магические коэффициенты жестко зашиты;
   - нет объяснения баллов для каждого `HotDeal`;
   - нет централизованной конфигурации параметров анализа.

3. Ограничения качества данных:
   - несовершенное извлечение бренда/модели/памяти;
   - `SellerName` практически не используется;
   - `AuthorLogin` применяется только для blacklist;
   - blacklist/проверка коммерческих объявлений смешаны с анализом.

## Проверенные исследовательские вопросы

1. Какие возможности и ограничения имеет текущий парсер 999.md?
2. Какие сигналы действительно работают для поиска горячих предложений?
3. Как снизить ложные срабатывания blacklist и commercial detection?

## Рекомендованные задачи

### 1. Повысить устойчивость парсера

* Ввести версионирование парсера/API:
  - добавить `ParserVersion` и `LastApiUpdate` в класс `WebScraperService` или в лог.
  - сохранить ключевые поля запроса и дату последнего успешного сбора.

* Исправить `IsBlockedResponse`:
  - считать блокировку `true` только при статусе 403/429 или явных Cloudflare/anti-bot маркерах;
  - не считать заблокированным «короткий» HTML без ошибок, если это нормальный ответ.

* Упростить и обезопасить сбор деталей:
  - если возможно, заменить регулярные выражения на парсинг JSON из страницы;
  - добавить проверку `OwnerLogin`, `PhoneNumber`, `Description` на пустоту и fallback.

* Сделать сбор метаданных более прозрачным:
  - отдельная структура `ListingDetails` для `PhoneNumber`, `SellerName`, `AuthorLogin`, `Views`, `Description`.
  - логировать сколько объявлений получилось с деталями и сколько без них.

### 2. Сделать скоринг понятным и настраиваемым

* Вынести коэффициенты и пороги в конфигурацию или константы:
  - `priceDeviationWeight`, `freshnessBonus`, `viewsBonus`, `urgencyBonus`, `defectPenalty`, `retailPenalty`.

* Добавить класс `ScoreComponents` или `DealScoreBreakdown`:
  - `BaseScore`, `PriceScore`, `RetailAdjustment`, `FreshnessScore`, `ConditionPenalty`, `TotalScore`.
  - сохранять это для каждого `HotDeal`.

* Сделать формулу прозрачной в UI:
  - выводить краткий текст, почему предложение попало в `HotDeals`.
  - добавить поле `ScoreExplanation` в модель `HotDeal`.

### 3. Улучшить blacklist и коммерческую классификацию

* Перенести правила `CommercialMarkers` и `UrgencyMarkers` в отдельный модуль `ListingClassifier`.
* Разделить blacklist на:
  - `PhoneNumberBlacklist`,
  - `AuthorLoginBlacklist`,
  - `ChronicSellerBlacklist`.
* Добавить метрики для `ChronicSeller` и `AuthorLogin`:
  - количество объявлений,
  - частота появления,
  - суммарный объём продаж.

### 4. Усилить качество модели данных

* Добавить больше моделей брендов и улучшить `ExtractModel` для других производителей.
* Улучшить `ExtractStorage` для дополнительных вариантов (`GB`, `TB`, `ГБ`, `ТБ`, `512g`, `1tb`).
* Нормализовать телефоны и логины до одного стандарта.

### 5. Документировать и тестировать

* Оформить `Prompts/SmartphoneMonitor_DeepResearch.md` и `SmartphoneMonitor_ImplementationPlan.md`.
* Написать unit-тесты для ключевых функций:
  - `ExtractModel`, `ExtractBatteryHealth`, `DetectDefectsAndEstimateRepair`, `NormalizePhone`, `IsAccessoryOrPartOrOther`.
* Добавить запись `reports/parsing_audit.log` или CSV с метриками сбора.

## Предложенный порядок работ

1. подготовить инфраструктуру настроек/логов для парсера;
2. исправить проверку блокировки и детализацию объявления;
3. вынести scoring в отдельный компонент с пояснениями;
4. стабилизировать blacklist/коммерческие правила;
5. добавить тесты и зафиксировать результаты.

## Как использовать

* Этот план можно использовать как дорожную карту при работе над `SmartphoneMonitor`.
* После каждой группы изменений тестировать сбор и анализ на реальных данных.
* При изменении сайта 999.md достаточно проверить `ParserVersion` и скорректировать `WebScraperService`.
